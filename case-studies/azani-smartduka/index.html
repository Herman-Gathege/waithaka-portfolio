01

Overview

Azani SmartDuka is a lightweight SaaS system for shops, marts, hardware stores and other sales-driven small businesses. Owners manage inventory, record sales, track supplier purchases and follow up customer credit from a single dashboard, across one branch or several.

It is built as a REST API with a React single-page application on top: a Flask and SQLAlchemy back end over PostgreSQL, Celery and Redis for background work, and a mobile-first interface designed for fast point-of-sale use. The front end is deployed on Vercel and the API on Render.

02

The problem

Many small shops still track stock by hand or in notebooks. That leads to inaccurate inventory, lost sales data, poor supplier records and credit sales that are hard to chase.

Any replacement had to be simple enough for a busy counter, work on the phone a shop owner already has, keep each business’s data strictly separate, and be ready for Kenya Revenue Authority electronic tax invoicing (eTIMS).

03

My contribution

  • Built the product across the stack together with Herman Gathege, from the React interface to the Flask APIs behind it.
  • Worked on sales processing with automatic inventory deduction, so every sale updates stock without a separate step.
  • Built stock tracking across branches, supplier purchase records and customer credit with debtor management.
  • Worked on reporting: sales summaries, profit estimates, stock history and inventory insights, with staff performance attribution.
  • Kept the point-of-sale screens mobile-first, so the common tasks take as few taps as possible.

SmartDuka is a two-person build with Herman Gathege. A detailed breakdown of who built which part is available on request.

04

Approach

  • Multi-tenant by organisation: every record belongs to an organisation, with authentication and organisation-level authorisation, so one business can never see another’s data.
  • API-first: Flask and SQLAlchemy APIs back sales, inventory, customers and reporting, and the React app consumes them as a client — keeping business rules on the server.
  • Slow work off the request path: Celery workers with Redis handle background operations such as invoice transmission, so a sale completes instantly even when an external service is slow.
  • Tax-ready from the start: the invoicing flow is designed around KRA eTIMS electronic tax invoice integration rather than bolted on later.
  • Built for the counter: a mobile-first React interface optimised for quick point-of-sale workflows.

Where it stands

I have not published usage or revenue figures here. If you would like a walkthrough of the product or the code, I am happy to arrange one.

08

Key takeaways

  • For small retailers, speed at the counter decides whether a system gets used at all; every extra tap on the sale screen is a reason to go back to the notebook.
  • Background jobs are what make external integrations such as tax invoicing safe to depend on — the shop never waits on someone else’s server.
  • Designing for organisations from the first table keeps multi-tenancy simple; adding it later means touching every query.
